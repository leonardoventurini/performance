# Meteor 3.5 Reliability Conformance Audit

## Status

Proposed implementation specification for direct rollout.

This document supersedes the scope of
`specs/2026-07-27-change-stream-conformance-audit.md` for release-level
conformance. The existing document remains the contract for the implemented
bounded CRUD audit until this specification is delivered.

## Goal

Create one automated, reproducible release audit that determines whether an
exact Meteor 3.5 release conforms to a declared set of:

- Change Streams observer selection and document-observation semantics;
- observer fallback behavior;
- DDP data and transport integrity over SockJS and uWebSockets.js;
- DDP session resumption and fresh-session recovery;
- Change Stream restart and MongoDB topology recovery;
- deterministic synthetic-data and concurrency cases;
- release, package, runtime, and topology identity requirements.

The output is evidence for a release decision, not a throughput ranking. A
release-level pass means every required capability for the declared scope was
exercised and passed. Latency, CPU, memory, network volume, and database
resource measurements remain diagnostic unless a case declares a correctness
deadline before execution.

## Outcome

The completed system exposes one command:

```sh
just release-audit 3.5.1-beta.0
```

The command validates its environment, executes the entire applicable
conformance matrix, persists every case result, aggregates a release manifest,
and exits nonzero unless the manifest is `conformant`.

The dashboard displays the manifest and its cases and may request the same
canonical coordinator through its single-flight server control plane. The
browser never executes audit code or supplies raw process,
environment, database, path, checkout, or output arguments. While execution is
active, the dashboard displays the coordinator's durable real-time progress
stream.

## Risk and assurance level

This is high-risk test infrastructure because its output may be used to claim
distributed data integrity and release readiness. A false pass is more harmful
than an incomplete result.

The design therefore fails closed:

- missing evidence is `incomplete`, never `passed`;
- an unknown or mismatched release identity is `incomplete`;
- an unexecuted required capability is `incomplete`;
- an expected fallback using the wrong driver is `non_conformant`;
- an injected fault that cannot be proven to have occurred is `incomplete`;
- a case that crashes still persists an incomplete evidence record;
- a topology outside the declared manifest is not silently generalized.

## Scope

### Required release claim

The first complete claim is:

> The pinned Meteor 3.5 release conforms to the declared Change Streams,
> observer fallback, DDP transport, DDP session-resumption, and recovery
> contracts on the exact MongoDB server version, feature compatibility
> version, and replica-set topology recorded by the manifest, over SockJS and
> uWebSockets.js.

The default claim does not include sharded clusters. Sharded-cluster support
is a separate scope dimension and may be declared only when the sharded
topology suite is configured and all of its required cases pass.

### Included

- Exact published Meteor releases and exact Meteor source checkouts.
- Exact tested MongoDB server and feature compatibility versions satisfying
  Meteor's documented MongoDB 6+ requirement, on a replica-set topology.
- Optional exact tested MongoDB sharded topology with an explicit claim
  dimension.
- SockJS WebSocket transport.
- SockJS HTTP fallback where the test environment can force it.
- uWebSockets.js transport.
- Default and explicitly configured reactivity order.
- Supported unordered observers.
- Ordered and incompatible-query fallback.
- Initial snapshots, live mutations, selector transitions, projections,
  observer sharing, and cleanup.
- Brief disconnect resumption, queue overflow, grace expiry, HCP behavior,
  and sticky/non-sticky routing.
- Change Stream closure, recoverable errors, primary step-down, election, and
  temporary database disconnection.
- Deterministic EJSON and adversarial BSON-compatible values.
- Independent MongoDB, DDP-client, and Meteor-instrumentation evidence.
- Negative controls that demonstrate the oracles detect corruption.

### Excluded from the release claim

- Raw MongoDB Change Stream features not exposed by this declared Meteor
  publication surface, including expanded events and pre-images.
- MongoDB collection rename, drop, drop-database, and invalidate semantics as
  successful Meteor live-query features.
- Multi-region latency, throughput capacity, or production sizing.
- Arbitrary third-party DDP transports.
- Browser UI rendering correctness beyond the DDP and Minimongo state oracle.
- Exact production proxy behavior unless its topology is explicitly included.
- A guarantee covering MongoDB or Meteor versions not present in the manifest.

Excluded features must remain visible as `out_of_scope` unless an explicit
target-source contract supports the stronger `not_supported` classification;
they must not disappear from the report.

## Definition of complete

A release audit is complete only when:

1. The release manifest has an exact identity and contract digest.
2. Every required capability maps to at least one executed case.
3. Every topology and transport coordinate required by capability
   applicability completed.
4. Every hard-gate oracle passed.
5. Every injected fault has independent activation evidence.
6. Every negative control failed for the intended reason.
7. No required capability is `not_exercised`.
8. No case is `incomplete`.
9. Cleanup and topology restoration passed.
10. The aggregate artifact is internally consistent and schema-valid.

The word `conformant` is reserved for this state.

## Terminology

- **Capability**: A stable, versioned behavior declared by Meteor or by this
  audit's integrity contract.
- **Case**: One executable test of a capability under one explicit
  configuration.
- **Variant**: A transport, observer order, topology, workload, or fault
  coordinate applied to a case.
- **Oracle**: An independently produced assertion used to decide a hard gate.
- **Negative control**: An intentional mutation proving an oracle can detect a
  representative violation.
- **Fault witness**: Evidence produced by the fault controller or target
  system showing that the requested fault occurred.
- **Release manifest**: The aggregate, immutable description and outcome of
  one complete audit.

## Result states

### Release states

- `conformant`: all required cases passed and all completion rules hold.
- `non_conformant`: at least one required case produced valid failing
  evidence.
- `incomplete`: execution or evidence was missing, ambiguous, unverifiable, or
  outside the declared environment.

### Case states

- `passed`: every hard gate for the case passed.
- `failed`: at least one hard gate produced valid failure evidence.
- `incomplete`: the case could not establish a valid pass or fail.
- `not_applicable`: the contract declares that the case does not apply to this
  manifest coordinate.

### Capability states

- `passed`: all required mapped cases passed.
- `failed`: at least one required mapped case failed.
- `incomplete`: a required mapped case was incomplete or not executed.
- `verified_fallback`: an explicitly expected fallback selected the required
  fallback driver and preserved correct behavior.
- `not_supported`: the target Meteor contract explicitly does not expose the
  feature.
- `out_of_scope`: the manifest deliberately narrows the release claim.

`not_supported` and `out_of_scope` are never converted into `passed`.

## Architecture

### CLI and coordinator

Add a `release-audit` command in `cli/` and a dedicated driver in `drivers/`.
The coordinator:

1. Loads and validates the release contract.
2. Resolves the exact case matrix.
3. Performs all non-destructive preflight checks.
4. Starts topology services where configured.
5. Executes cases with bounded concurrency.
6. Persists each case atomically as soon as it finishes.
7. Restores the affected topology after every case.
8. Aggregates the release manifest.
9. Validates manifest completeness.
10. Exits nonzero for `non_conformant` or `incomplete`.

The existing `audit` command remains a fast bounded case runner. The
`release-audit` command composes all required cases and is the only command
allowed to emit a release-level conformance status. Dashboard launch requests
resolve to this same command through the server control plane; they do not
create a second execution or decision path. Audit-capable deployments rely on
trusted network or platform access controls rather than an application-level
API key.

### Real-time progress channel

The coordinator owns one append-only progress stream per audit:

```text
coordinator
  -> local durable progress journal
  -> bounded asynchronous publisher
  -> dashboard ingestion method
  -> dashboard progress collection
  -> DDP publication
  -> live audit view
```

The initial transport constants are:

- `PROGRESS_HEARTBEAT_INTERVAL_MS = 2_000`;
- `PROGRESS_STALE_AFTER_MS = 10_000`;
- `PROGRESS_BATCH_MAX_EVENTS = 100`;
- `PROGRESS_BATCH_MAX_BYTES = 256 * 1024`.

The dashboard server exposes authenticated method
`releaseAuditProgress.ingestBatch` and publication
`releaseAuditProgress.byAudit`. It stores summary state in
`releaseAuditRuns` and immutable sequenced events in
`releaseAuditProgressEvents`. These names are public integration contracts and
receive method/publication contract tests.

Writing the local journal is part of the coordinator state transition.
Publishing to the dashboard is asynchronous and never blocks workload,
fault-controller, oracle, cleanup, or artifact persistence. Dashboard
unavailability does not change a case result; it changes live-delivery health
and the publisher retries from the last acknowledged sequence.

The journal uses newline-delimited, runtime-validated `AuditProgressEvent`
records and is included in the release artifact. Events have a strictly
increasing sequence number. Dashboard ingestion is idempotent on
`(auditId, sequence)`, rejects conflicting duplicates, and returns the highest
contiguous acknowledged sequence. Reconnection resumes from the next sequence.

Journal append is crash-consistent:

1. Serialize and runtime-validate one complete event.
2. Append the event and newline.
3. Flush and `fsync` the journal.
4. Only then expose the corresponding coordinator transition or enqueue the
   event for dashboard delivery.

Recovery scans from the beginning, validates every record and sequence, and
may truncate only an invalid final partial record caused by a torn append.
Interior corruption, sequence gaps, conflicting duplicates, or an invalid
complete final record make the audit incomplete. After valid tail recovery,
the next event uses `lastValidSequence + 1`.

State transitions, heartbeats, fault activation/restoration, oracle sealing,
case completion, cleanup, and audit completion are lossless events.
High-frequency diagnostic counters may be coalesced to at most one event per
second per case. Coalescing never changes hard-gate evidence.

The publisher has a bounded in-memory queue and reads overflowed events from
the journal. It applies exponential retry with a fixed maximum interval.
Audit completion does not discard an unacknowledged tail. The publisher must
either:

- deliver through the manifest's `lastSequence` and receive a contiguous
  acknowledgement; or
- persist a delivery outbox lease containing the audit ID, dashboard target,
  journal path, and next sequence so a later publisher or explicit artifact
  ingestion resumes delivery.

Dashboard event retention cannot archive or remove the active stream until
the final manifest is ingested, its journal digest and sequence boundary are
reconciled, and the dashboard acknowledges every sequence through
`lastSequence`. Dashboard outage remains non-blocking and does not weaken the
release conformance result.

Finalization order is:

1. append and `fsync` the terminal `audit_completed` or `audit_aborted` event;
2. close the journal;
3. calculate its digest and first/last sequence boundary;
4. atomically persist the release manifest containing that progress reference;
5. enqueue or resume delivery of the sealed tail and manifest.

The terminal progress event does not contain the manifest digest, avoiding a
digest cycle. The dashboard reconciles its stored sequence range and journal
digest against the manifest.

Dashboard ingestion authentication reuses the existing benchmark API-key
boundary. Read access is intentionally public, matching the existing public
benchmark dashboard, but only after strict sanitization. The publication
requires an exact audit ID, applies fixed document and byte limits, and
publishes only allowlisted fields. Clients cannot directly insert, update, or
remove progress or manifest records.

Runtime schemas reject unknown keys and enforce required keys per event kind,
non-negative safe-integer counters, 128-character identifier limits,
256-character stable reason-code limits, and a 4 KiB serialized event ceiling.
Case events require both `coordinate` and `attemptId`; global audit events
forbid them. Fault events require matching fault identity. Only sealed
`case_completed`, `audit_completed`, and `audit_aborted` events may carry a
terminal status.

The same allowlist, bounds, and redaction rules apply to local journal replay,
dashboard publication, manifest ingestion, minimized reproductions, and
failure reasons. MongoDB URIs, credentials, environment dumps, generated
document bodies, private settings, tokens, absolute home paths, and
secret-looking keys or values are rejected rather than merely hidden in the
UI.

### Live dashboard experience

Add a dedicated route for an active or completed release audit. While active,
it displays real state:

- exact Meteor, harness, MongoDB, topology, observer, and transport identity;
- overall state and last coordinator heartbeat;
- completed, running, failed, and incomplete logical-case counts;
- the current case coordinate and attempt;
- the current case state-machine step;
- acknowledged writes, subscribers ready/converged, oracle assertions, and
  bounded diagnostic counters where available;
- active fault, activation witness, restoration state, and recovery deadline;
- hard-gate outcomes as they are sealed;
- cleanup and topology-restoration state;
- live-delivery health, last received sequence, and any detected sequence gap;
- final release status and artifact identity after aggregation.

The UI does not show guessed completion percentages, synthetic progress,
placeholder stages, or speculative ETAs. Before a measurement exists, the
field is omitted or states the exact blocking condition. A stalled heartbeat
is displayed as `progress stream stale`; it does not imply that the audit
process stopped.

Opening the page after execution starts replays the stored event stream and
then follows live DDP updates. Refreshing the page preserves this behavior.
After completion, the same route transitions to the immutable manifest view
and retains the event timeline for diagnosis.

### Proposed module ownership

- `reliability/contracts/`
  - versioned capability manifests and runtime schemas;
- `reliability/cases/`
  - case definitions and deterministic expected outcomes;
- `reliability/oracles/`
  - MongoDB snapshot, DDP ledger, observer selection, and session evidence;
- `reliability/faults/`
  - bounded fault controllers and fault witnesses;
- `reliability/topology/`
  - replica-set, sharded, standalone, and proxy lifecycle adapters;
- `reliability/generators/`
  - deterministic values, document schemas, operation schedules, and shrinkers;
- `reliability/release-audit/`
  - matrix resolution, execution state machine, aggregation, validation, and
    durable progress journal;
- `tests/reliability/`
  - integration and topology cases;
- `tests/unit/reliability/`
  - schema, state-machine, generator, aggregator, and negative-control tests;
- `apps/tasks-3.x/packages/bench-monitors/`
  - narrowly scoped Meteor probes unavailable outside the process;
- `apps/dashboard/`
  - progress ingestion/publication, active audit view, release manifest, and
    per-case evidence presentation.

Existing modules under `reliability/` should migrate into these responsibilities
without maintaining parallel sources of truth.

### Execution state machine

Each case uses the following states:

```text
declared
  -> preflighted
  -> environment_ready
  -> clients_ready
  -> workload_running
  -> fault_activated?
  -> converging
  -> evidence_sealed
  -> cleanup_verified
  -> passed | failed | incomplete
```

Invalid transitions are rejected and persisted as `incomplete`. A case cannot
become `passed` before evidence is sealed and cleanup is verified.

The release coordinator uses:

```text
planned
  -> identity_verified
  -> executing
  -> aggregating
  -> conformant | non_conformant | incomplete
```

A previously failed or incomplete attempt cannot be overwritten by a later
pass. A logical coordinate contains an ordered set of uniquely identified
attempts. Capability mapping targets the logical coordinate and aggregates its
attempts using the frozen policy:

- any valid behavioral failure makes the coordinate `failed`;
- otherwise any infrastructure or evidence-incomplete attempt makes it
  `incomplete`;
- otherwise every attempt must pass.

Retries add attempts; they never replace evidence.

### Data and EJSON integrity

Required cases cover:

- ASCII and empty strings;
- composed and decomposed Unicode;
- right-to-left text;
- emoji and surrogate-pair boundaries;
- null, booleans, zero, negative zero, and numeric boundaries supported by
  EJSON;
- dates;
- Object IDs;
- binary values;
- empty, nested, wide, and high-cardinality objects;
- empty, repeated, nested, and large arrays;
- compressible and seeded incompressible payloads;
- documents near the configured conservative BSON ceiling;
- field removal without stale client residue;
- replacement without stale client residue;
- concurrent changes to distinct fields;
- hot-key changes;
- multiple documents with identical projected state.

The generator records both BSON and DDP-safe canonical digests. Subscribers
recompute canonical digests from received values rather than trusting digest
fields carried inside the document.

### Transport integrity

Required over both SockJS and uWS:

- connection negotiation identifies the selected transport;
- publication readiness;
- added, changed, and removed delivery;
- frame/message byte evidence for every required event class;
- exact EJSON round trip;
- 512 KiB payload delivery and one near-ceiling document whose measured BSON
  size is between 11 MiB and the audit's 12 MiB safety ceiling;
- deterministic raw-socket fragmentation for WebSocket-based SockJS and uWS;
- slow-consumer convergence;
- abrupt socket loss;
- concurrent subscriber fanout;
- bounded reconnect storm;
- clean client shutdown;
- clean server shutdown.

SockJS polling fallback is required only when the manifest includes
`sockjs-polling`. It must be forced and independently identified rather than
inferred from configuration.

Compression is a separate capability. It may be required only after the
harness can independently measure compressed and uncompressed bytes. A zero
compressed-byte counter is `incomplete`, not proof of no compression.

Fragmentation is injected below the WebSocket layer by the local proxy using
the repeating TCP write-size schedule `1, 7, 64, 1024` bytes in both
directions. The proxy records requested and observed chunk sizes, byte totals,
and connection identity. The DDP oracle must decode the same canonical
messages and content digests as the unfragmented control. This case does not
claim WebSocket-message or SockJS-application-frame fragmentation and is not
applicable to the HTTP-polling coordinate.

### DDP session resumption

Required over SockJS and uWS:

- `session.resume.within_grace_period`
  - same server connection ID;
  - `sessionResumed === true`;
  - no new server `onConnection` invocation;
- `session.resume.subscription_preserved`
  - no second `sub` request;
  - no full republish;
  - queued changes arrive exactly once;
- `session.resume.inflight_method_replayed`
  - an unacknowledged method is replayed;
  - the server execution ledger records one or more attempts as permitted by
    Meteor's retry contract;
  - an audit method carrying a stable idempotency key produces one durable
    effect despite repeated attempts;
  - the client receives one terminal result;
- `session.resume.auth_context_preserved`
  - authenticated identity and connection-scoped context remain correct;
- `session.resume.grace_expired`
  - new connection ID;
  - `sessionResumed === false`;
  - fresh subscription converges exactly;
- `session.resume.queue_boundary`
  - `limit - 1` queued server messages resumes;
  - exactly `limit` queued server messages resumes;
  - `limit + 1` queued server messages discards the session and establishes
    clean fresh state;
- `session.resume.hot_code_push`
  - resumption is intentionally skipped;
  - fresh state is correct;
- `session.resume.sticky_instance`
  - reconnect to the owning process resumes;
- `session.resume.non_sticky_instance`
  - reconnect to another process does not falsely resume;
  - fresh state converges without duplication;
- `session.resume.concurrent_storm`
  - all resumable sessions resume;
  - all expired/overflowed sessions restart cleanly;
  - no cross-session data leakage.

The network controller must terminate the underlying connection
non-gracefully. Calling the public graceful disconnect API does not establish
session-resumption behavior.

An unacknowledged Meteor Method is eligible for replay on the controlled
successful reconnection case, and its server execution may occur one or more
times. This is not a global delivery guarantee and the audit must not claim
exactly-once server execution. It proves the documented retry behavior in the
controlled case and uses an idempotency token to make the fixture method's
durable effect exactly once. A second case without idempotency accepts either
one or multiple server executions and verifies that the observed count agrees
with the attempt ledger; it does not require a duplicate.

The queue oracle counts the exact outbound messages accepted into the
suspended session queue, excluding transport keepalives and messages rejected
before enqueue. The target release contract freezes this counting seam from
the DDP server source before execution. Queue instrumentation and the
reconnected client's decoded ledger must agree on `limit - 1`, `limit`, and
`limit + 1`.

### Change Stream recovery

Required recovery cases:

- unexpected Change Stream close;
- recoverable Change Stream error;
- repeated close/error with configured restart delay;
- MongoDB primary step-down;
- successful replica-set election;
- temporary Meteor-to-Mongo network interruption;
- recovery while writes continue;
- recovery while a DDP client is disconnected;
- startup snapshot concurrent with writes;
- watch setup concurrent with writes;
- change-stream restart concurrent with writes;
- catch-up timeout followed by eventual convergence.

Every recovery case requires:

- fault activation evidence;
- observer restart or explicit expected fallback evidence;
- acknowledged write ledger;
- DDP event ledger;
- exact final MongoDB/DDP state convergence;
- no permanent write-fence stall;
- bounded recovery deadline;
- topology restoration evidence.

Resume-token history loss or an unrecoverable stream error is included only if
the target release declares behavior for it. Otherwise it is recorded as an
exploratory case and cannot affect the release claim.

### Raw MongoDB features outside the declared publication surface

The registry includes the following as `out_of_scope` unless an explicit
target-source reference establishes a stronger classification:

- collection rename/drop/invalidate;
- database drop;
- expanded events;
- change-stream pre-images.

For each entry, the contract records a source specific to that entry and why
it is not exposed by the declared Meteor publication surface. The audit does
not infer a stable rejection guarantee from absence in general documentation.
If Meteor later exposes one, changing its expectation requires a contract
revision and new required cases.

## Workload model

### Serialized conformance lane

For operations that promise an observable state transition:

1. Record the intended mutation and canonical expected state.
2. Apply one acknowledged database write.
3. Require every subscriber to observe the exact transition.
4. Seal per-subscriber evidence.
5. Continue only after the hard gate passes or times out.

Every attempt is retained. Once a capability attempt fails, later attempts
cannot overwrite it.

### Concurrent convergence lane

For burst, recovery, and backpressure cases:

1. Generate a deterministic operation schedule.
2. Record every acknowledged write.
3. Permit legal intermediate coalescing.
4. Reject per-document revision regression and foreign-run events.
5. Compare each subscriber's final canonical state against MongoDB.

Exact intermediate DDP event count is not a hard gate where Meteor is allowed
to coalesce current-state updates.

### AI-assisted synthetic corpus

AI may propose adversarial schemas and operation sequences offline. Proposed
cases enter a reviewed corpus only after they are:

- normalized into a deterministic schema;
- assigned a stable identifier;
- bounded by document, operation, memory, and duration limits;
- checked for EJSON and MongoDB validity;
- given an explicit expected outcome;
- reproducible without network access or an AI service;
- shrinkable to a minimal failing sequence.

The runtime generator uses only committed corpus definitions plus a seeded
pseudo-random schedule. Model name, prompt, and generation timestamp may be
retained in corpus provenance, but are never required to replay the case.

### Concurrency schedules

The corpus includes:

- independent-document writes;
- repeated hot-document writes;
- concurrent writes to disjoint fields;
- replacement racing with updates;
- removal racing with updates;
- selector entry/exit oscillation;
- client disconnect during each mutation class;
- stream recovery during each mutation class.

Schedules are generated from a seed and stored as bounded operation metadata.
Failures retain the schedule and a minimized reproduction.

## Independent oracle model

### MongoDB oracle

Produced outside Meteor:

- acknowledged operation ledger;
- authoritative final snapshot;
- canonical document digests;
- database build and topology identity;
- primary/election timeline;
- current profiler state;
- current collection and run-scoped document counts.

### DDP-client oracle

Produced from decoded protocol traffic:

- connection and session identifiers;
- inbound/outbound message classes;
- subscription requests and ready messages;
- per-client logical event ledger;
- EJSON-decoded canonical values;
- per-document revision transitions;
- method request/result lifecycle;
- reconnect and `sessionResumed` state;
- final Minimongo-equivalent state.

### Meteor probe oracle

Produced by narrowly scoped test instrumentation:

- actual observer class for every audited cursor;
- fallback transitions and reasons;
- multiplexer and handle lifecycle;
- connection creation/closure counts;
- session creation, suspension, resumption, expiry, and queue-overflow state;
- write-fence start, timeout, release, and completion state;
- Change Stream open, close, error, restart, and generation identifier.

Meteor probes cannot alone prove content integrity because they are inside the
system under test.

### Fault-controller oracle

Produced by the infrastructure that injects the fault:

- requested fault and target;
- activation time;
- independently observed effect;
- restoration time;
- final restored topology.

A requested fault without an observed effect makes the case `incomplete`.

## Correctness invariants

The following are release hard gates:

- Every mutation and cleanup selector is scoped to the current run.
- Every acknowledged serialized mutation is observed exactly as required by
  every applicable subscriber.
- No subscriber observes a lower revision after a higher revision for the same
  document.
- No subscriber observes a foreign run.
- Every subscriber's final canonical state equals MongoDB's final canonical
  state.
- Payload, structure, BSON/EJSON type, and field-presence digests agree.
- Removed or replaced fields do not remain stale in client state.
- Every audited cursor selects the expected observer.
- Every fallback case selects the exact expected fallback.
- Every required DDP message class has decoded message and byte evidence.
- A resumed session preserves the documented identity and subscription/method
  semantics.
- A fresh session is never reported as resumed.
- Fault cases prove both activation and recovery.
- No case passes with missing, malformed, or contradictory evidence.
- Cleanup restores run-scoped data and all altered database/profiler settings.

## Identity and provenance

Preflight records and validates:

- requested Meteor release or checkout;
- output of the exact Meteor binary used to launch the app;
- `.meteor/release`;
- digest of `.meteor/versions`;
- target Meteor checkout SHA when applicable;
- harness commit SHA and dirty state;
- Node.js version;
- operating system and architecture;
- MongoDB server version and feature compatibility version;
- topology and member roles;
- DDP transport configuration and actual transport;
- reactivity order and actual observer selection;
- capability-contract identifier and digest;
- workload corpus identifier and digest;
- fault-controller version.

Release identity must never be `system`, `unknown`, or inferred only from a
fixture file. A dirty harness is permitted only when explicitly requested for
development; its release result is always `incomplete`.

Secrets, credentialed URIs, host tokens, and private settings are never stored.

## Topology matrix

### Required replica-set matrix

Every case runs against the exact MongoDB server version and feature
compatibility version declared by its manifest coordinate. That coordinate
must satisfy Meteor's documented MongoDB 6+ requirement and use a replica-set
topology where Change Streams are available.

Transport dimensions:

- SockJS;
- uWS.

Observer-order dimensions:

- default order, verified as `changeStreams,oplog,polling`;
- explicit `changeStreams,oplog,polling`;
- explicit `oplog,changeStreams,polling` for precedence verification;
- explicit `changeStreams,polling` for direct fallback verification.

The versioned capability registry contains the explicit applicability map.
Transport-independent observer semantics run on one declared reference
transport unless their applicability explicitly claims both. Transport and
session capabilities run on every transport they claim. Recovery capabilities
run on every topology they claim. No implicit Cartesian product is inferred.
The resolver must reject a manifest with an uncovered applicable coordinate.

### Required fallback topology

A standalone MongoDB case with
`changeStreams,oplog,polling` configured must select polling and preserve
live-query correctness because neither Change Streams nor same-database oplog
tailing is available. Change Streams-to-oplog fallback is tested separately on
a replica set where oplog tailing is valid and Change Streams is made
deterministically inapplicable by the case contract. A fallback case may never
point `MONGO_OPLOG_URL` at a database identity different from `MONGO_URL`.

### Optional sharded-cluster claim

When `sharded_cluster` is declared, repeat:

- observer semantics;
- both transports;
- mongos interruption;
- shard primary step-down;
- recovery with writes in flight;
- exact final convergence.

Replica-set results cannot satisfy sharded-cluster capabilities.

### Multi-process Meteor topology

Session stickiness cases use two distinguishable Meteor processes and a
controllable proxy:

- sticky reconnection to the owning process;
- forced reconnection to the non-owning process;
- explicit session outcome and final-state convergence.

Transport documentation does not generally require affinity for uWS
connectivity, but session resumption still requires reconnection to the same
physical Meteor process holding the suspended session. The audit therefore
requires affinity specifically for the positive resumption claim over both
SockJS and uWS.

Managed or serverless MongoDB branding is never treated as a topology. The
manifest records the exact provider deployment type and observed topology; a
result applies only to that observed configuration.

## Fault injection

Faults must be bounded, reversible, and targeted. Controllers may:

- close an audited Change Stream through a test-only Meteor probe;
- cause a test-only recoverable stream error;
- use replica-set administration to step down the primary;
- isolate Meteor from MongoDB through a local proxy;
- terminate a DDP socket through a local network proxy;
- route a reconnect to a chosen Meteor process;
- trigger an HCP-compatible code-version change in the fixture.

Controllers must not:

- drop production collections or databases;
- alter a non-audit deployment without explicit remote authorization;
- kill broad or unresolved process groups;
- log credentialed connection strings;
- leave profiling, network rules, or topology settings modified.

Each controller has `preflight`, `activate`, `witness`, `restore`, and
`verifyRestored` operations. Restoration runs in `finally` and again during
coordinator recovery if the case process disappears.

## Safety and resource limits

- Loopback MongoDB is the default.
- Remote targets require an explicit allow flag and an exact database name.
- Destructive fault cases require an isolated topology marked disposable.
- Every database mutation includes `runId`.
- The audit collection is never dropped.
- Profiles cap subscribers, documents, mutations, BSON bytes, generated
  bytes, event-ledger bytes, execution time, and fault duration.
- Evidence logs use fixed-size records and bounded failure arrays.
- Long-running release audits stream real case progress and persist completed
  cases immediately.
- Live dashboard publication uses a bounded queue backed by the durable
  progress journal; dashboard slowness cannot apply backpressure to the audit
  workload.
- A coordinator lease and run registry identify interrupted runs.
- A cleanup command accepts an exact run ID and refuses broad deletion.
- Startup detects orphaned topology or profiler state and stops before
  execution until restoration succeeds.

## Evidence storage

The canonical root result envelope remains compatible with the dashboard.
Release-level artifacts live under:

```text
results/release-audits/<release>/<audit-id>/
  manifest.json
  cases/<case-coordinate>.json
  evidence/<case-coordinate>/<oracle>.json
  reproductions/<failed-case>.json
```

`results/` remains ignored. CI uploads the directory as an immutable artifact.

Writes are atomic:

1. write a temporary file in the target directory;
2. flush and close it;
3. rename to the final path;
4. record its digest in the parent artifact.

The release manifest includes only bounded summaries and artifact digests.
Raw payloads are excluded unless a minimized failure reproduction needs them.

## Aggregate decision algorithm

The aggregator:

1. Validates every case schema.
2. Validates release, contract, corpus, and topology identity consistency.
3. Rejects duplicate `(coordinate, attemptId)` pairs.
4. Aggregates every logical coordinate from its immutable attempt set.
5. Resolves every capability's required applicable coordinates.
6. Marks missing or incomplete required coordinates as capability
   `incomplete`.
7. Marks any valid required behavioral failure as capability `failed`.
8. Marks fallback capabilities `verified_fallback` only when the expected
   fallback and content oracles pass.
9. Preserves `not_supported` and `out_of_scope`.
10. Validates the negative-control registry digest and requires every control
    to be detected for its exact expected reason.
11. Validates cleanup, restoration, and progress-journal evidence.
12. Produces:
    - `non_conformant` if any required capability failed;
    - otherwise `incomplete` if any required capability, negative control,
      recovery artifact, or progress artifact is incomplete;
    - otherwise `conformant`.

Failure is monotonic. Retrying a failed case creates another attempt and does
not erase the original. The initial policy is `all_attempts_must_pass` using
the logical-coordinate aggregation rules defined above. A negative control
that unexpectedly passes or fails for the wrong reason invalidates the
decision oracle and makes the release `incomplete`; it is not evidence that
Meteor itself is non-conformant.

## Negative controls and oracle sensitivity

The audit suite includes deterministic mutations that must fail:

- drop one DDP `changed` event in the serialized lane;
- duplicate one logical event;
- deliver a lower revision after a higher revision;
- alter one payload byte after decoding;
- retain one field removed by projection or replacement;
- report a configured observer instead of the actual observer;
- suppress one fallback record;
- claim session resumption for a new session ID;
- apply an idempotency-keyed method effect twice;
- omit a fault witness;
- omit release identity;
- return a nonzero workload process with valid-looking passing JSON;
- remove one required case from the release manifest;
- fail cleanup or topology restoration.

Each mutation test must fail for its named stable reason. A negative control
that unexpectedly passes blocks the release audit implementation.

## Observability and abort conditions

The coordinator emits structured progress events:

- manifest planned;
- case preflight started/completed;
- environment ready;
- clients ready;
- workload progress;
- fault requested/activated/restored;
- convergence progress;
- evidence sealed;
- cleanup verified;
- case completed;
- release aggregate completed.

Abort the current case and mark it incomplete when:

- release or topology identity changes;
- a process exits unexpectedly;
- the database enters an undeclared topology;
- a requested fault lacks a witness;
- evidence exceeds configured bounds;
- cleanup cannot be confirmed;
- a harness, environment, or evidence-acquisition deadline expires before a
  valid behavioral decision can be made.

A declared correctness deadline is different. If the target remains
observable but fails to deliver, converge, resume, or recover within that
deadline, the case is `failed` with
`correctness_deadline_exceeded`. Only loss of the ability to decide makes the
case `incomplete`.

Abort the entire release audit when:

- identity or contract validation fails;
- topology restoration fails;
- profiler or network state cannot be restored;
- an unsafe or ambiguous database target is detected;
- artifact storage cannot persist completed evidence.

## Recovery and rollback

This feature adds test infrastructure and no application-data migration.
Rollback is code-level: revert the release-audit commit while retaining case
artifacts for diagnosis.

Operational recovery:

1. Stop new case scheduling.
2. Restore the active fault controller.
3. Stop audit clients and Meteor processes.
4. Restore MongoDB topology and profiler settings.
5. Delete only documents matching the exact run ID.
6. Verify no coordinator lease, proxy rule, or test process remains.
7. Persist an incomplete case and incomplete release manifest.

If automatic recovery fails, print exact non-secret inspection and restoration
commands and exit nonzero. Never continue to another case on a topology whose
restoration is unverified.

- [ ] Add a local connection proxy and DDP protocol oracle for SockJS, forced
  SockJS polling, and uWS; verify actual transport identity, decoded event
  ledger, byte evidence, fragmentation, slow consumer, and abrupt loss; done
  when every declared transport coordinate passes independently.
- [ ] Add session lifecycle instrumentation and resumption cases for grace,
  subscriptions, methods, auth context, queue boundaries, HCP, sticky routing,
  non-sticky routing, and reconnect storm; verify connection IDs, client
  resume flags, server lifecycle, subscription/method ledgers, and final
  state; done when every session capability passes over SockJS and uWS.
- [ ] Add replica-set and network fault controllers with preflight, activation
  witness, restoration, and restoration verification; verify close, error,
  primary step-down, election, network interruption, startup/watch/restart
  races, and catch-up timeout; done when every recovery case contains a valid
  fault witness and exact convergence evidence.
- [ ] Add the `release-audit` coordinator, atomic case persistence, progress
  journal/events, asynchronous dashboard publisher, leases, interrupted-run
  recovery, and aggregate decision algorithm; verify crash, retry, disk
  failure, duplicate attempt, missing case, event replay, sequence conflict,
  torn final journal record, interior corruption, dashboard outage,
  post-completion outbox drain, secret-looking/oversized/unknown event fields,
  unauthenticated ingestion, direct-write denial, and monotonic failure
  behavior; done when no failure path can emit conformant and dashboard
  availability cannot block execution.
- [ ] Add all negative controls and run them against the real decision path;
  verify each mutation fails with its named reason; done when unexpected
  negative-control success blocks the suite.
- [ ] Add authenticated progress ingestion, live DDP publication, release
  manifest ingestion, active-audit rendering, and evidence rendering to
  `apps/dashboard`; verify late join, refresh, reconnect/replay, sequence gap,
  stale heartbeat, dashboard outage, conformant, non-conformant, incomplete,
  verified-fallback, unsupported, out-of-scope, and unknown-schema fixtures;
  done when live state is real and resumable and the UI never conflates result
  states.
- [ ] Add `justfile`, README, AGENTS, workflow, and operator documentation for
  the complete command and recovery procedures; verify every documented

  pinned local replica-set release claim and CI retains its artifacts.
- [ ] Run `just check-all`, negative controls, the complete pinned release

  the manifest reports zero failed, incomplete, or unexercised required
  capabilities and all restoration checks pass.

The checklist is one integrated rollout. A release-level conformance label is
not introduced until the entire checklist and verification gauntlet are
complete.

## Acceptance criteria

The implementation is accepted when:

- `just release-audit <exact-release>` produces a schema-valid manifest;
- the manifest cannot be conformant with an unknown release, dirty harness,
  missing required case, missing fault witness, missing cleanup proof, or
  failed negative control;
- all declared replica-set Change Streams cases pass;
- all required fallback cases select the exact expected fallback;
- SockJS and uWS transport-integrity cases pass;
- all required session-resumption and fresh-session cases pass;
- all required recovery cases pass with witnessed faults;
- every required capability is passed or verified fallback;
- unsupported and out-of-scope capabilities remain explicit;
- all artifacts are bounded, non-secret, internally digested, and retained;
- the dashboard streams sequenced real progress without blocking the audit,
  replays missed events, and renders the aggregate without weakening result
  semantics;
- the repository test suite and the complete pinned live audit pass.

## Main uncertainty

The highest uncertainty is how much test-only instrumentation Meteor 3.5
exposes for deterministic Change Stream close/error injection and DDP session
lifecycle observation. Before implementation, inspect the exact target source
for stable seams. If no narrow seam exists, add fixture-local probes through
the smallest reversible wrapper around the concrete driver/session methods.

Do not infer recovery or resumption solely from client convergence. Without
driver/session lifecycle evidence, those cases remain incomplete.

## Stop conditions

Revise this specification before implementation continues if:

- the target release's source contradicts the documented contract;
- deterministic session or Change Stream fault injection requires changing
  Meteor production behavior rather than fixture-local instrumentation;
- a topology cannot be restored reliably after injected failure;
- uWS or SockJS cannot be independently identified at runtime;
- an independent MongoDB/DDP oracle cannot be maintained;
- evidence volume cannot remain bounded without discarding a hard-gate fact;
- a sharded-cluster claim is requested without an isolated sharded topology.
